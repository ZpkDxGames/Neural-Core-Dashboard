# Security findings and remaining qualifications

## Corrected in this candidate

- **Unbound old grants:** migration 004 invalidates historic grants. Private engine consumption checks action, immutable intent, exact subject/revision, session family, Google identity and both authorization epochs inside the decision transaction. Loading a schema-004 database with the old engine refuses owner consumption.
- **Table-wide grant mutation inherited from 003:** 004 revokes runtime table UPDATE and grants only `UPDATE(used_at)`. Runtime cannot rewrite action/session/intent/epoch/expiry bindings. Issuer/admin functions are unavailable to the API role.
- **Replay and confused deputy:** actual TLS certificate pins, cnf binding, fixed service JWT issuer/audience/algorithm/key and exact request digest. Durable SQL JTI consumption, strict paths/queries/JSON, owner registry and primary session checks prevent a browser-supplied identity/proof from becoming authority.
- **False freshness:** distinct Google authorization requests `max_age=0`. Signed `auth_time`, same immutable owner, current session, one-use state/browser binding, nonce, PKCE and challenge creation boundary are all required. Missing/stale claims fail; token issue time never substitutes.
- **Cursor revocation:** note/graph and proposal cursor scopes bind credential hash, permission epoch, session/consent epoch, current role/scopes and query. A rotated credential cannot reuse an outstanding cursor even when its role/scopes remain the same.
- **Cross-action decisions and stale permissions:** one-use grants bind action and intent; scope/credential/role changes advance epochs, invalidate cached identities and outstanding delegated work. Agent role names cannot select owner authority. Runtime permissions are reloaded for every operation.
- **Uncertain publication:** grant/decision/outbox/receipt commit atomically; publication stays pending until the existing worker acknowledges bytes/hash. Lost completion responses recover the same receipt without duplicate revisions. Expired completed challenges can still supply their receipt under current authorization; expired unused challenges cannot issue.
- **Credential delivery failures:** a bounded private sink write rolls back credential/proof/receipt on failure. No raw credential is returned to the browser. Rotation changes credential hash and epoch. Revocation does not depend on the secret sink. Stale agent proposals stay unverified.
- **Outage resource retention:** ten-second request context is checked around SQL and before commit; primary family and sink waits are bounded. No positive authorization cache or unbounded retry exists. Outages map to explicit non-success states.
- **Private data lifetime in the tab:** no automatic synchronization or persistent remote cache. Disconnect, offline and owner-session broadcasts abort outstanding requests and discard late results. Source evidence remains unresolved unless independently authorized.

## Development limitations, not passed certifications

1. **Real Google step-up is not qualified.** The actual protocol library is exercised with synthetic signed RSA ID tokens and JWKS, including missing/stale freshness rejection. This does not prove that the existing Google client/account will produce a qualifying auth_time, force a fresh owner interaction, accept the new callback or support the selected hosting origin. Fresh issuance stays disabled by default. If real behavior fails, keep it unavailable; never relax freshness to iat/account selection/silent login.
2. **No private network is provisioned or certified.** Tests use disposable loopback TLS certificates and synthetic identities. Hosting support for TLS 1.3, client certificate custody, private ingress, server/workload pin rotation and online session-store access require separate staging evidence. Flags are operator attestations, not automatic certification.
3. **Trusted issuer boundary:** the BFF validates Google signed claims and asserts the verified identity/freshness over its pinned mTLS service path. The separate issuer role trusts that workload after gateway verification. This is not a claim of Byzantine resistance to a fully compromised BFF, issuer, database administrator or private host. Splitting an independently verifying OIDC issuer is a future defense-in-depth option, not an implemented second verifier.
4. **Single-owner private service:** application scopes and least-privilege roles are tested. No public/multitenant RLS claim is made. Synthetic policy permits one active non-revoked synthetic agent per owner; an expired credential remains denied until explicit rotation/revocation. Real ChatGPT/Claude/Gemini connections are absent.
5. **OS/filesystem limits remain:** external uncooperative editors do not participate in SQL locking. Existing exclusive writer/quiescence policy still applies. The 10k checkpoint cap is preserved; no 100k physical-vault, paired encrypted SQL+vault recovery, real Obsidian Desktop or shared-VPS/Minecraft capacity certification is claimed.
6. **Finite synthetic tests:** browser/axe checks and software GPU rendering do not replace manual screen-reader, real mobile, penetration, key-custody or real-account testing. New private browser views use explicit synthetic HTTP fixtures; the separate backend end-to-end test uses actual loopback mTLS, PostgreSQL semantics, signed synthetic OIDC and physical Markdown publication.
7. **Operational logs and retention:** identifiers/receipt hashes remain private in SQL under existing owner retention policy. Replay/quota cleanup is bounded; expired challenges/receipts need an operator-reviewed retention plan. No scheduled cleanup or backup operation was activated.

No real credentials, user memory, providers, VPS/DNS/Caddy/Cloudflare services, Minecraft or PlexonPanel infrastructure were changed. Main/preview and drafts #4–#8 are preserved. This document authorizes no activation.
